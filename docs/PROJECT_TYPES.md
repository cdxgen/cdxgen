# Project Types

## Overview

The following **Project Types** are supported:

- When in `CLI` mode, passed as `t` or `--type` flag
- When in `Server` mode, passed as `projectType` parameter.

_Note: there are multiple project types / aliases that will produce the same output_

_*NOTE:*_

> - Apache maven 3.x is required for parsing pom.xml.
> - gradle or gradlew is required to parse gradle projects.
> - quarkus plugin is automatically detected and used by parsing pom.xml files (since cdxgen version 11.0.5) for java types. To explicitly specify this type, use `-t quarkus`. This is especially needed when cdxgen is invoked with `--no-recurse` argument for performance reasons.
> - sbt is required for parsing scala sbt projects. Only scala 2.10 + sbt 0.13.6+ and 2.12 + sbt 1.0+ are currently supported.
>   - Alternatively, create a lock file using sbt-dependency-lock [plugin](https://github.com/stringbean/sbt-dependency-lock)
> - sdkman must be installed and setup to use Java version types such as `java8`, `java11`, `java25`, and `java26`.
> - sdkman is also used to provision pinned JVM build tools passed as versioned types such as `-t maven3.9.9`, `-t gradle8.14`, `-t sbt1.10.11`, or `-t scala3.6.4`. A compatible JDK is installed automatically when the current Java is too old for the pinned tool. Pass `--feature-flags jvm-tool-setup` to derive the toolchain from the repository (`.sdkmanrc`, wrappers, `project/build.properties`) instead.
> - While python3.6 is supported (-t python36), dependency tree construction requires python >= 3.9
> - rbenv must be installed and setup to use the new Ruby with version types such as ruby2.5.4, ruby3.4.0
> - For Ruby, a precompiled native gem is identified by the `platform` purl qualifier and not by a platform suffix in the version. `google-protobuf (3.25.1-x86_64-linux)` in a `Gemfile.lock` becomes `pkg:gem/google-protobuf@3.25.1?platform=x86_64-linux` with the version `3.25.1`, as required by the [gem purl type](https://github.com/package-url/purl-spec/blob/main/types/gem-definition.json). Every native build of a gem is reported as its own component, since each has its own checksum. The implied default platform `ruby` is never emitted.
> - For Ruby, cdxgen enriches gems from the caches already on the machine before making any network call: bundler's compact index cache under `$BUNDLE_USER_CACHE/compact_index` supplies the sha256 and the required ruby and rubygems versions of the exact build, and the installed gemspecs under `GEM_HOME/specifications` supply licenses, description and project URIs. A `CHECKSUMS` section in `Gemfile.lock` (bundler 2.5+) is used directly. Unlike the registry lookups, all of this also works in `--dry-run` mode and offline.
> - For Ruby, a gemspec in the scanned directory describes the gem the project builds, and becomes `metadata.component` with its description, authors, licenses, project URIs, and `cdx:gem:*` properties. An `email` address is attached to an author only when there is one address per author or a single author. The gem's own sightings, the gemspec and the `PATH remote: .` entry that the Gemfile `gemspec` directive adds to `Gemfile.lock`, are folded into `metadata.component` instead of being listed as components, and their dependency edges move with them. A version assigned from a constant such as `Foo::VERSION` is read from the `version.rb` file the gemspec requires, and otherwise the version Bundler locked is used. `#{spec.name}`, `#{spec.version}`, and `#{spec.homepage}` in URIs are expanded, and a URI that still holds an interpolation is dropped. With `--project-name`, this applies only when the name is the gem's; `--project-version` sets the version of `metadata.component`.
> - For Ruby, a gem is a `library` unless it ships executables, which make it an `application`; this applies to `metadata.component` too, so a gem keeps its type whether it is scanned or depended on. The executables are read from a literal `executables` list, or, when the gemspec computes them as the `bundle gem` template does, from the files in its `bindir`. A gem is a `framework` only when cdxgen's curated list names that exact gem, such as `rails` or `sinatra`; a description that mentions a framework is not enough. `cdx:gem:remote` is the source a gem is locked against in its own `Gemfile.lock` entry, not the source of a gem that merely depends on it. A gem locked against `https://rubygems.org` gets a `distribution` external reference to its `.gem` file even offline, since that URL follows from the name, version, and platform.
> - For Ruby, with `--spec-version 1.7` (the default), the `required_ruby_version` of the gems becomes one `platform` component, `pkg:generic/ruby`, marked `isExternal` because the deployment environment provides it. Its `versionRange` is the intersection of the requirements in the `vers` syntax, such as `vers:gem/>=3.3` or `vers:gem/>=3.1|<4` for `~> 3.1`, and every component that declares a requirement depends on it. Each gem's own requirement stays in `cdx:gem:rubyVersionSpecifiers`. Earlier spec versions cannot mark a component as external, and a container image ships its own Ruby, so neither gets the component.
> - For Ruby, the project's `.bundle/config` is honoured. `BUNDLE_PATH` is used to locate the installed gems, and cdxgen warns when `BUNDLE_WITHOUT` shows that some bundler groups were never installed, since those gems are missing from the BOM.
> - For Node.js, a version with semver build metadata (`1.0.0+build.5`) is kept as `package.json` and the lockfile record it, and percent-encoded in the purl (`pkg:npm/app@1.0.0%2Bbuild.5`). `npm publish` records `semver.clean()` of the version (`1.0.0`), so when the two differ the component also carries `cdx:npm:cleanedVersion` with the form the npm registry knows it by. The same applies to npm, pnpm, yarn and bun lockfiles, the root component and workspace members included.
> - For Node.js workspaces, every workspace member is a dependency of the root and has its own dependency entry built from its `package.json`. yarn v1 writes no `yarn.lock` entries for workspace members, so their dependencies are resolved against the lock file entries for the ranges each member declares.
> - For .NET, a project file's version comes from the properties `dotnet pack` uses: `PackageVersion`, else `Version`, else `VersionPrefix` with an optional `-VersionSuffix`, with the legacy `ProductVersion` as the last fallback. A version that still references an MSBuild property such as `$(BuildNumber)` is not reported, and the root falls back to `latest`.
> - `hbom` is a dedicated host inventory mode. Do not mix it with SBOM/OBOM project types in the same invocation; generate HBOM separately using `hbom` or `cdxgen -t hbom`.
> - For `collider.lock`, cdxgen captures direct dependencies plus the locked package inventory, but Collider lockfiles do not currently encode full package-to-package transitive edges. cdxgen therefore models the graph as completely as the source format allows without inventing unsupported relationships. See [8] and [9].
> - For Swift, packages that only the root package's test targets (or library targets that only tests depend on) use are scoped `optional`, together with the packages reachable only through them in `swift package show-dependencies`, so `--required-only` leaves them out. With `--evidence`, a package that the sources are found to use is promoted back to `required`. Swift evidence builds the project with SwiftPM and indexes it with SourceKitten; see [EVINSE.md](EVINSE.md).
> - For .NET projects, deep evidence uses the optional `dosai` binary bundled through `@cdxgen/cdxgen-plugins-bin`. Use the cdxgen container images or install a compatible .NET SDK when local dosai execution is required.
> - For Rust, `Cargo.lock` is by design the union of every dependency kind and every target triple, so it cannot on its own say which crates are dev-only or platform-gated. cdxgen recovers the dependency kind per edge and rolls it up per component: from `cargo metadata`'s resolve graph with `--deep`, and from the workspace manifests otherwise. A crate is treated as dev-only, and so scoped `excluded` for `--required-only`, only when every path reaching it from a workspace member crosses a dev edge. Build dependencies and proc-macros are compiled for the build host, so they carry `cdx:cargo:hostOnly` and are moved out of `components[]`, which describes the delivered assembly, into the `formulation` section, which describes how the assembly was produced. This happens by default; `--include-formulation` adds them to the full formulation section, and without it a minimal formulation entry is created so nothing is lost. Their bom-refs stay resolvable, so the dependency graph is unchanged. Set `CDXGEN_CARGO_TARGET` (or cargo's own `CARGO_BUILD_TARGET`) to a target triple to resolve the graph for a cross-compiled target; see [ENV.md](ENV.md). With `--evidence`, `--required-only` runs after the evidence stage, so an optional crate that rusi observed in the sources is promoted to `required` rather than filtered out. `--deep` additionally records the features the resolver enabled (`cdx:cargo:resolvedFeatures`), which say which code is compiled rather than which features the manifest declares, and emits a component for each native C library a `-sys` crate links: its version is recovered from the providing crate's semver build metadata (`openssl-src@300.6.1+3.6.3` ships OpenSSL 3.6.3) or from a version define in the vendored C source, and `cdx:cargo:linkage` says whether the library is compiled into the artifact or expected from the deployment environment, the latter also carrying `isExternal` on CycloneDX 1.7+. A crate resolved from a registry other than crates.io carries that registry as a `repository_url` purl qualifier, because a private registry can publish a name that also exists on crates.io. The `cargo` BOM-audit rule pack asserts on all of this; see [BOM_AUDIT.md](BOM_AUDIT.md).
> - Svelte and SvelteKit projects are scanned with the Node.js types (`-t js`, `-t svelte`, or `-t sveltekit`). `.svelte` components are segmented position-preservingly so imports recover at true file/line evidence, SvelteKit virtual modules (`$app/*`, `$env/*`, `$service-worker`) are attributed to `@sveltejs/kit`, `$lib/*` resolves through `kit.alias`, `svelte.config.*` is parsed for adapter and preprocessor evidence, `<style lang>` blocks imply the matching CSS preprocessor and their `@use`/`@import` package references, and rune usage (`$state`, `$derived`, ...) marks `svelte` required even without an import. When the optional `@appthreat/atom-parsetools` package is installed, template expressions additionally become usage occurrences; scope correctness never depends on it.

Use of the container image is recommended in all these cases, since it has the build tools pre-installed.
